# M4.6 — 150 output tok/s before M5

Status: the original matched HTTP benchmark exceeds 150 tok/s, 2026-09-18.
An independent server restart measured **157.82 / 162.35 tok/s**. The additional
four-workload set measures **111.60 tok/s combined**, so general-workload 150
tok/s is not achieved. M5 starts from this explicitly bounded baseline.

The primary boundary remains one request, A100-SXM4-40GB, BF16 target,
explicit input IDs, 128 generated tokens, HTTP wall time including prefill,
no response or prefix cache, and the unchanged numerical regression gate.
Aggregate throughput is not a substitute for single-request throughput.
Speculative decoding, if used, must report the method, acceptance, overhead,
and output parity. Repetitive-input speedups are not general workload claims.

Baseline: `artifacts/m45-acceptance.json`. Runtime snapshot before experiments:
`artifacts/m46-base-src/`. The prior measured result is preserved in
`M4_5_PRISM_PERFORMANCE.md`.

Investigations:

- Tune the remaining packed integer GEMV bottleneck across actual layer shapes.
- Improve short-prefill and speculative verification paths where warranted.
- Inspect compatible draft availability and hybrid GDN speculation support.
- Keep acceptance failures and unsuccessful performance experiments visible.

The public `prism-ml/Ternary-Bonsai-2-27B-gguf` file listing inspected on this
date contains no dedicated drafter. Older Bonsai/Qwen-derived drafters must not
be assumed compatible with this target. The installed vLLM 0.29.0 uses V1 for
ngram speculation and V2 for DSpark; state rollback and actual runner choice
must be validated before claiming acceleration.

A wider Hub search found the independent Bonsai-specific
[ProCreations DFlash2 adapter](https://huggingface.co/ProCreations/Ternary-Bonsai-2-27B-DFlash2).
Downloaded only config, BF16 safetensors and provenance/license files, pinned at
`8cc7a436ef7637a0655a692245c0696713a6af4f`. The 1.924B-parameter checkpoint hash
`c6f94f2e8d9b4111645d5bd78845289dbc77b0215f7a139f8bfe55f28cc2a0b9`
was verified. Its manifest's target SHA-256 matches our original PQ2_0 exactly.
This is stronger evidence of compatibility than the model name, but actual
acceptance, GDN state behavior and latency still require local measurement.
No downloaded native binaries or scripts are executed.

The cold-cache DP4A tile search is recorded in `artifacts/m46-tune.json`.
It tests 60 configurations on each of merged FFN gate/up, down, and LM head.
Results are isolated kernel times and cannot be summed into an asserted model
throughput. The current tile is already near the best on gate/up and LM head;
down has more room. A separate experimental tensor-core kernel evaluates
multi-token verification while preserving per-32 Q8 scales and INT32 dot sums.

## Experiments so far

- DFlash2 with three draft tokens and the unchanged integer target: **75.39 /
  78.56 tok/s** on the two original HTTP cases. All nine frozen continuations
  plus a repeat after state reuse match. This does not meet 150 tok/s.
  `artifacts/m46-dflash2-first/` contains outputs, counters and the greedy gate.
- INT8 per-Q8-group MMA, TF32x3 dequantized MMA, FP16 high/low MMA and a shared
  DP4A prototype were measured. They were slower than the relevant baseline
  on the tested shapes. Some floating variants also exceeded the separate
  tight DP4A numerical criterion; those failures remain recorded. These kernels
  are experimental and are not selected for model serving.
- Paired 16-bit PQ2 decode preserves the integer arithmetic and improves some
  isolated shapes, but is not by itself a measured solution to the model target.

## Marlin candidate

`BONSAI_VERIFY_KERNEL=marlin` adds an **additional runtime INT4 cache** for
multi-token projections. PQ2 symbol `c` encodes `c-1`; Marlin `uint4b8` code
`c+7` encodes exactly the same integer. Scales are unchanged FP16 values, with
layout permutations only. All 65,536 packed eight-symbol patterns were checked
for exact re-encoding, including reordered output rows. The source safetensors
and original PQ2 runtime weights remain intact. This increases VRAM consumption;
it is not a claim to retain the 7 GiB runtime footprint.

The activation transform still computes in FP32, then stores FP16 for Marlin.
Marlin uses FP32 reduction and deterministic non-atomic output, returning FP16
before the model activation cast. This is a distinct numerical path, checked
against the FP32 projection definition with a stated relative-L2 bound of
`5e-4`; it does not inherit the tighter integer/FP32 kernel claims. Existing
DP4A and FP32 tests are unchanged. The full-model 2% TV gate is also unchanged.

At eight input rows the LM-head operator measured 0.55 ms via Marlin versus
11.96 ms via the existing larger-batch FP32 fallback. These are operator times,
not an end-to-end speed claim. The combined model results follow.

## Selected configuration and measured results

Use the integer backend for one-row decode and Marlin for multi-row projections,
with DFlash2 proposing seven tokens per verification round. The original PQ2
safetensors remain the storage format. The extra INT4 cache and BF16 drafter
raise model loading memory to about 23.73 GiB; the configured process uses about
34 GiB on the 40 GiB A100. This is not the previous 7 GiB serving footprint.

All rates below are 128 output tokens divided by median HTTP wall time, including
prefill, after one warmup and three measured repetitions, one request at a time.
Temperature is zero, EOS is ignored, prefix caching is disabled. Output token
IDs are stable across repetitions. The controls use the same Marlin prefill and
integer single-row target, without the drafter.

| Input | With DFlash2, tok/s | Without drafter, tok/s | Same 128 output IDs? |
| --- | ---: | ---: | --- |
| Original raw 0 | 157.82 | 75.18 | Yes |
| Original raw 1 | 162.35 | 75.11 | Yes |
| Code | 171.83 | 75.04 | Yes |
| Korean explanation | 87.24 | 75.05 | No; first difference at token 34 |
| Reasoning | 134.57 | 74.94 | Yes |
| Narrative prose | 89.85 | 75.06 | No; first difference at token 38 |

The original pair also measured 157.55 / 161.86 tok/s on the earlier server
launch. Their combined rate is 160.05 tok/s on the final run. The four additional
cases combine to 111.60 tok/s (total tokens / sum of median request times).
These are fixed 128-token prefixes, not completed-answer quality evaluations.
The additional corpus was frozen before its measurements in
`tests/data/m46/workloads.json` and was not used for training.

Original-benchmark counters: 220 draft rounds, 1,540 proposed tokens, 808
accepted, 52.47% acceptance, mean 4.67 tokens per round including the bonus token.
Acceptance and prompt length make performance workload-dependent. Seven draft
tokens outperform the five-token candidate (144.83 / 144.47 tok/s).

## Correctness and limits

- Full unchanged gate: **9/9** frozen greedy continuations, **33/33** next-token
  top-1 decisions, all 248,320 log probabilities finite per decision, maximum TV
  **0.0180077631**, below the existing 0.02 threshold.
- HTTP gate: all nine continuations and a repeated request after state reuse pass.
- **117 tests passed**, including exact PQ2-to-INT4 re-encoding, Marlin projection
  accuracy and CUDA graph replay. Existing integer/FP32 tolerances were unchanged.
- Source hashes in the parity record match the selected runtime.
- Long greedy sequences are **not guaranteed identical** to the no-drafter
  control. Korean and narrative outputs diverge at the positions above. Single-row
  Q8 arithmetic and multi-row FP16 Marlin arithmetic differ; the specific causes
  of these two divergences have not been isolated. Short-gate success is not a
  proof of full-distribution or long-sequence equivalence.
- General-workload 150 tok/s, long context, prefix caching, concurrent speculative
  serving, TP, vision and drafter training are not validated by this milestone.

Evidence: `artifacts/m46-acceptance.json`, `artifacts/m46-final-repeat/`,
`artifacts/m46-marlin-dflash7-retry/`, `artifacts/m46-no-draft-control/`,
`artifacts/m46-final-parity.json`, `artifacts/m46-tests-before-model.log`.
The summary explicitly records `expanded_benchmark_150_passed: false`.

## Reproduction

From the repository root, with the pinned draft artifacts described above:

```bash
source .venv/bin/activate
BONSAI_BACKEND=integer BONSAI_VERIFY_KERNEL=marlin \
vllm serve converted/bonsai2-pq2 \
  --host 127.0.0.1 --port 8000 --served-model-name bonsai2 \
  --dtype bfloat16 --max-model-len 2048 --max-num-seqs 4 \
  --max-num-batched-tokens 128 --gpu-memory-utilization 0.85 \
  --no-enable-prefix-caching --enable-chunked-prefill \
  --attention-backend FLASH_ATTN \
  --compilation-config '{"mode":0,"cudagraph_mode":"FULL_DECODE_ONLY","cudagraph_capture_sizes":[8,16,24,32]}' \
  --speculative-config '{"method":"dflash","model":"artifacts/m46-dflash2","num_speculative_tokens":7}'
```

The owned-server benchmark shuts down its server even on failure:

```bash
BONSAI_VERIFY_KERNEL=marlin .venv/bin/python tools/m45_compare.py \
  --engine integer --gpu-memory-utilization 0.85 \
  --speculative-config '{"method":"dflash","model":"artifacts/m46-dflash2","num_speculative_tokens":7}' \
  --output artifacts/m46-reproduction --validate \
  --extra-corpus tests/data/m46/workloads.json
```

Use a new output directory for each run. The default backend remains `triton`;
the faster path is explicitly opt-in. No benchmark server is left running.
